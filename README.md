## 文本纠错服务（text-correction）

基于 FastAPI 的 PDF / 文本 / 合同纠错服务：待校对文本就是模型眼里的一份源码文件（`000.txt`），模型像改代码那样读它、给它打小补丁，改哪一处、坐标多少由服务端确定性算出。支持中文错别字、英文拼写等纠错，以及 DOCX 合同模板填空字段审查。

### 纠错机制

模型对代码修改做过大量训练，但对"输出坐标"没有——实测让它自己数下标会数偏（把 3444 报成 3430）。所以这里让模型做它擅长的事（当文件改），把"这处原文在哪儿"留给代码：

1. **建文件**：待校对文本原样落成 `000.txt`，模型眼里就是一份只读源码；它改出来的版本记在 `001.txt`。`000.txt` 任何时候都不变，所以改动落地后坐标不会漂移。
2. **自己读**：模型用 `read_text` 决定看哪儿、看多少（不填参数就接着没读过的地方往下读，返回 `  1234|正文` 这样的带位置行），用 `find_text` 查一段引文出现在哪、唯一不唯一。读到哪儿由服务端记账，`finish` 会检查有没有漏读的区间。
3. **写补丁**：改动直接写在正文里，形态照抄 Codex 的 `apply_patch`——```@` 行是逐字照抄的引文（只用来定位），`-`/`+` 两行才是"哪儿错了、改成什么"。模型不报位置、不报序号、不数任何东西。
4. **定位**：服务端拿引文在 `000.txt` 里搜，必须**有且仅有一处**；要改的那一处由"引文位置 + 改前那行在引文里的位置"算出，模型说的位置一律不采信。表格那条路不用引文——模型抄行首那个跨表唯一的编号，见下面「表格纠错」。
5. **错误类型门**：每处改动都必须能机械归到一类错别字（见下），对不上就不执行。
6. **比对出结果**：`000.txt` 与 `001.txt` 逐字符对齐比对——某位字符变了是 `replace`，某位字符没了是 `delete`，位置一律是 `000.txt` 的绝对下标。纠错结果不靠模型自报。

一轮的结束条件不依赖模型的自我评价：`finish` 先查覆盖率，漏读的区间原样打回去让它接着读；再查"块写错了"的欠账——引文没抄准、引文不唯一、引文里没有改前那行、引文里有多处都说得通、块格式不对：这几类不是"这处不算错别字"的判决，门还没判到内容，只是模型这次没把块写对，所以只要还挂着就不让 `finish`（同一批最多连打回 `BACKLOG_MAX` 次，免得某处引文永远抄不准时把轮次烧光）；既不读也不改的轮次连着出现两次才收工；`TOOL_MAX_TURNS` 为正数时最多来回这么多轮（0 表示不设上限，轮数按片算、片长由 `MAX_TEXT_LENGTH` 卡住，与整份文档多长无关）。被拒绝的改动连同原因回灌给下一轮，措辞是"换一个能对上原文的改法再试"。

实测（整份一次跑）：

| 用例 | 结果 | 轮次 | 耗时 |
| --- | --- | --- | --- |
| 13,276 字客户合同 `_已填充.docx` | 每次都命中的是中过→中国、广东生→广东省、科技元→科技园；模板自带的「及尾款款前」原样不动。跑三次分别落地 3 / 4 / 6 处，多出来的全在「多打的字」这一类（证据最弱，见下） | 26~29 | 19~26s |
| 6,927 字《货物零星采购合同（2025年版）》（人工植入 6 处错字） | 6/6 命中：假→甲、删「航」（开户航行→开户行）、海男省三亚是→海南省三亚市、删「你」（卖你方→卖方）、买→卖、款款款款款→款 | 16 | 21.2s |

两份都走到 `finish`、覆盖率 100%。客户合同里落在条款措辞上的改动是 **0**：唯一一处"看着像重复字"的「及尾款款前」原样留下——同一份文件里「预付款前」出现过两次，说明 `款`+`前` 本来就是全文在用的搭配（模型这一轮确实提了删「款」，被门按这条判据挡回来了，见下）。

两个反直觉的坑都写进代码了：提示词里**不能**报"全文共多少字、你读到了百分之几"——实测模型一看到"才读了 11%"就跳读，同一段文字放进整篇会漏、单独喂给它反而能抓到；`read_text` 返回的位置行只带绝对下标，不带进度。

#### 错误类型门

哪些改动可以落地，不靠模型自报，而靠从改动本身算出来的确定类型（`correction/typo_types.py`）：

| 类型 | 判据 | 例 |
| --- | --- | --- |
| 同音字 | 单字替换，原字与改后字读音相同（声调可同可异） | 中过→中国、科技元→科技园 |
| 近音字 | 单字替换，读音只差平翘舌或鼻韵尾（`zh/z`、`sh/s`、前后鼻音不分） | 搜→收、事→四、一→银、身→生 |
| 字母数字 | 单字替换，一侧是 ASCII 字母、另一侧是它的形近数字 | O→0、l→1 |
| 同字连写 | 同一个字连写了两个以上，删到只剩一个 | 款款款款款→款、卖方方仓库→卖方仓库 |
| 多打的字 | 删掉一个汉字，它与前后相邻的字都不同 | 开户航行→开户行、卖你方→卖方 |
| 漏写的字 | 补上一个汉字，它和左右紧邻的字都不同、左右紧邻的都要是汉字，且它和左邻或右邻组成的两个字在全文别处出现过 | 邮编码→邮政编码 |

近音字先并平翘舌（`zh/z`、`ch/c`、`sh/s`），再归一韵尾 `n` / `ng`（前后鼻音不分：`一/银`、`身/生`、`民/明`）；单韵母音节不归一，所以 `安/啊`、`恩/饿` 不会被当成近音。

删字的分界线在"连写几个"：连着三个以上（`款款款款款`）删到剩一个；正好两个（`卖方方仓库`）要再看右边那个字——这个字和它组成的两个字要是在全文别处也出现过（`增值税税率`、`开户行行号`、`符合合同`、`预付款前`），说明这两个字分属两个词，是正常写法、不动；别处没出现过（`方仓`）才是多打了一个。孤零零一个字（`航行→行`、`卖你方→卖方`）删掉。删字只对汉字开放，数字连写（`5000`、`13800138888`）一个都不删。

实测（36,809 字客户 PDF）：全文两字连写 24 处，23 处是"分属两个词"的正常写法，靠"别处也出现过"这一条全部拦住；只有「卖方方仓库」右边那个字组不出词，按同字连写收掉一个。

"左右紧邻的都要是汉字"也是实测逼出来的：同一份 PDF 是按行抽出来的，很多行从词中间开始，模型看到「方应在收到买方的通知后7日内免费补齐短缺…」就要补「卖」（「卖方」全文到处都是），看到「术服务应符合合同的约定」就要补「技」，而上一行正好以那个字结尾——那只是换行把词切开了，一个字都不缺。一次跑下来它在 6 个这样的行首各补了一个字，全都是假的。判据只认汉字也是因为这个：整篇是把这些行用 `\n` 拼成一整段交给模型的，行首那个 `\n` 会被当成"左邻字"混过去。

"多打的字"这一类的波动也在实测里：13,276 字客户合同跑三次分别落地 3 / 4 / 6 处，多出来的都是这类删字（「乙方并不」删「并」、「直接承兑」删「承」、「应按全面履行」删「按」）。这类没有读音证据，只能校验"这个字和前后相邻的字都不同"，对不对得看上下文措辞（同一份 PDF 里「买方应按照」删「应」、「卖方方仓库」删「方」都是真的），所以它是六类里唯一允许有争议的一类。

六类之外一律不执行：一次补不止一个字、删一串互不相同的字（那是在改内容）、换个读音差得远的字（读起来更好，不是错字）、数字与编号（`3.1.1→3.1.2`、`3010→30`）、落在空格标点上的改动。这类改动不落地，只把"这处不算错别字"回灌给下一轮。

提示词里的评分是**按段算的，一段一段给分**（模型看到的一行就是一段）：这一段里的错别字一个不落、而且一个字都没改错，这一段才得分；漏掉一个、或者改错一处（把没写错的字改掉、删掉、补上），这一段都不得分——改错和漏掉一样重，整段作废。这样两条边一起压住：读的时候一段都不能跳，动手的时候只有十足把握才写。

判错标准也钉在同一处：**"平常人从头读一遍会不会觉得别扭"，不是语法书**。缺个"的"、少个量词、主语不完整、主动被动混用、语序还能调得更顺，这类平常人读着不别扭的一律不动；要删要补没有十足把握就别动（删错是把原文的字抹掉、补错是凭空多出一个字，最伤）。

提示词里不写"不要再提"：实测那样会让它连正确的改法也不敢试；要写成"换一个能对上原文的改法再试"。门是纯策略层，实现在 `correction/readtool.py` 的 `tool_edit_text`，判据在 `correction/typo_types.py`。

#### 改动块

一处改动 = 一个补丁段：```@` 逐字照抄原文（必须有且仅有一处），`-`/`+` 由若干"字级"动作搭出来——换 1 个字、删 1 个字、补 1 个字，或把一段 ≥2 个连写的字收成 1 个。一句话里错好几处、一段里掺着好几种动作都可以。

```
*** Begin Correction
@@ 甲    方：中过某某集团有限责任公司
-中过某某集团有限责任公司
+中国某某集团有限责任公司
*** End Correction
```

一处一段、可以写多段。服务端按下面的规则决定执不执行：

| 情形 | 处理 |
| --- | --- |
| 引文在原文里出现 0 次 | 拒绝，回灌"引文必须逐字照抄原文" |
| 引文在原文里出现 2 次以上 | 拒绝，回灌"前后多抄几个字，让引文唯一" |
| 引文里找不到 `-` 那行 | 拒绝 |
| 补字不是单个汉字、和左右相同、左右紧邻的不是汉字（挨着标点、换行、行首行尾）、或补出来的两个字全文别处没出现过 | 拒绝，回灌"这处不算漏字" |
| 删掉一串互不相同的字（含标点） | 拒绝 |
| 同一段里换字和增删糊在一起、说不清谁对应谁 | 拒绝，回灌"拆成两段分别写" |
| 一段里改了好几处字 | 逐处过类型门、逐处落地（海男省三亚是→海南省三亚市）；过不了门的那一处只它自己不落地，并回灌给模型 |
| 那处字过不了错误类型门 | 拒绝，回灌"这处不是错别字" |
| 引文里同一段出现多次、改哪处结果不一样 | 拒绝，回灌"改抄一段只包含一处的那几个字" |
| 同一处已经改过 | 拒绝，不重复落地 |

引文里同一段出现多次、但改哪一处结果都一样时，按最靠前的那处落地。

#### 工具

| 工具 | 参数 | 语义 |
| --- | --- | --- |
| `read_text` | `offset` / `length`（都可省） | 读 `000.txt` 的一段；不填就接着没读过的地方读，返回形如 `  1234|正文` 的带位置行 |
| `find_text` | `query`（1~60 字） | 查这段字在原文里出现在哪、前后是什么；拿不准引文唯不唯一时先搜一下 |
| `finish` | — | 声明全文读完、该改的都改完了；漏读的区间会被打回 |

改动本身不走工具——直接写在正文里。`read_text` 一轮最多把 4000 字新内容摆到模型眼前，这样"已计入已读"的内容一定真的给模型看过，覆盖率不会撒谎。补字走同一条路：只补一个汉字，且补出来的两个字要在全文别处出现过（邮编码→邮政编码），模型现编的搭配不会落地。标点、空格、数字、条款编号一律不动。

#### PDF 解析（`correction/pdf.py`）

用的是 **PyMuPDF**（底下是 MuPDF，C 实现）：一份 75 页的合同，把所有字符读出来只要几十毫秒。换成它之后，解析的耗时几乎全落在
**表格识别**上——MuPDF 的表格识别是 Python 写的，要逐页扫矢量线条、重建字符表，75 页约 1.7 秒。页与页互不相干，所以**按页切块丢给多个进程并行解析**（`PDF_PARSE_WORKERS`）：

- 逐页解析是确定的、跟别的页没关系，并行结果跟单进程逐页跑**完全一致**（`paragraphs` / `tables` / `blocks` 三份逐字比过，含表格的文档也比过）。
- 页眉要先知道“这一行在全篇出现过两次以上”，所以各页先把自己的第一行当候选报上来，页眉过滤、全篇表号都由主进程按页序拼回去——顺序跟单进程一模一样。
- 子进程崩了（内存不够之类）不会让整份文档解析失败：记一条 `pdf.parse.parallel_failed` 日志，退回单进程照样出结果。
- 表格照旧只认矢量线条、不靠文字位置猜表；一份表里被合并盖住的槽位是空的，靠它还原 `colspan` / `rowspan`，所以**表格张数跟换引擎前逐份对得上**（75 页那份 11 张、协议 3 张、扫描件 0 张，全对齐）。
- **并线容差 3 磅**（`LINE_TOP_TOLERANCE`）：同一个视觉行里，不同字体、页脚里的数字、目录点线的顶边能差出 2.9 磅；而真正相邻两行的行距最小也有 3.1 磅。差 3 磅以内算同一行——卡在 0 的话，一句话会被劈成两段分别送去纠错。
- 实测 75 页合同（71k 字）：单进程 2.0 秒、8 进程 0.5 秒（换引擎前分别是 5.7 秒和 1.4 秒）。

#### 外部解析（可选，`correction/parse2json.py`）

配了 `PARSE2JSON_BASE_URL` 就把「原文 → 段落 + 表格单元格」这一段交给外部的 DocParser（`POST /async/parse2json`，
异步提交 + 轮询）：它按版面做识别，块按阅读顺序出、表格自带行列与合并信息、扫描件也能 OCR 认字——恰好是本地
PyMuPDF 最弱的两处。它的输出会翻译成跟本地**完全同一形状**的 `paragraphs` / `tables` / `blocks`（逐页原始块给文字和
逐字方框，跨页合并块给表格的行列/合并信息），所以后面展平单元格、送纠错、结果页高亮一个字都不用改。

- 解析服务是自己按 URL 去下载原文的，所以要给它一个够得着的地址：`PARSE2JSON_FILE_URL`（带 `{doc_id}` 的模板，
  例如 `http://10.0.0.10:18081/api/document/{doc_id}`，走前端那个端口的 `/api`）；配了 `S3_PUBLIC_ENDPOINT`
  时优先用对象存储的签名地址，模板就可以不填。
- **这条模板只对「上传上来的文件」（`file`）用得上**：外部系统给的是链接（`fileUrl`）时，原链接
  原样转交过去，不用我们先把文件下载回来、再挂到一个解析服务够得着的地方。
- 转交就是转交：我们不下载、不转格式，它认不认这个链接是它的事——它报什么错（比如「这个链接不是
  PDF」）就原样回给调用方，HTTP 状态码按它那个 `errorCode` 的段位来（`4xxxx` 回 `400`、其余回 `500`），
  不乱改成我们自己的说法。
- 结果页要铺的那份原件（下载、Word→PDF 转换）跟等解析**一起做**：解析只能干等，取原件我们等得起，
  两件事没有先后依赖。实测同一份 PDF 链接 `total_ms` 从 17.0 秒降到 15.0 秒；解析失败时这活当场撤掉，
  不白占带宽和转换服务。
- 它回的方框是它自己那版渲染图上的**像素**（扫描件 A4 一页是 1190×1682，正好 72dpi 的 2 倍；
  有文字层的那种它直接用原生坐标，比例就是 1）。结果页是 PDF.js 按磅铺页、再把方框乘缩放贴上去的，
  所以拿到原件之后按「页宽 ÷ 图宽」逐页缩回去（`parse2json.rescale_to_points`）。不缩，扫描件的框
  就会大一圈、还整片偏到右下角去——比例逐页算，文档里混着不同尺寸的页也不会错位。
- **配了它就是唯一那条路**：没配能下载的地址、下载失败、服务报错（这个服务 **HTTP 状态码恒为 200，成败看信封里
  的 `errorCode`**）、等超时（`PARSE2JSON_MAX_WAIT_MIN`，默认 60 分钟），都直接报错（HTTP `500`，`detail` 写明是哪一步），
  **不退回本地解析**——两套解析给的结果不一样（分块、表格行列、扫描件认不认字），悄悄换一条，用户看到的
  纠错效果就跟着变。要跑本地那套，把 `PARSE2JSON_BASE_URL` 清掉或传 `PARSE2JSON_ENABLED=0`。
  只有一种不算失败：解析跑通、但这文档里一个可纠错的字都没有（没有文字层的扫描件、又没开 OCR）——
  那还是 HTTP `200` + 空的 `results`，跟本地解析碰上同样文档一个样。
  这次走的是哪条，看日志 `request.correction_file.parsed` 里的 `parser` 字段（`local` / `parse2json`）。
- 同理，配了解析服务之后 Word/Excel **必须先转成 PDF**（它只收 PDF）：转换服务不可用时直接报错，
  不再退回本地那套 docx 直读。
- 表格按「一页一张表」出（跟本地解析一个口径）：跨页的表格在合并块里是一整张，行号接着往下数，
  取到之后按页内最小值拉回从 0 开始，免得第二页那半边表顶上空出好几行。
- 页数上限默认交给服务端（1000 页，超了回 `41301`；本地那份 PDF 解析不受这个限制）。
  实测一份 6 页带表格的 PDF：排队 + 解析约 20 秒（含在解析服务那边的排队时间）。

#### 「解析」那一段到底是哪一段（转换 / 读文字 / 两处冷启动）

上传 Word 时，接口里的「解析」其实是两件事串起来的，日志和 `timings` 里分开记（`convert_ms` 是转换、剩下的才是读文字）：

| 文档 | Word→PDF 转换 | 读文字 + 表格 | 合计 |
| --- | --- | --- | --- |
| 14 KB 清单 `.docx` | 0.15~0.17 秒 | 0.02 秒 | 约 0.2 秒 |
| 26 页合同 `.docx` | 0.55~0.9 秒 | 0.14~0.2 秒 | 0.7~1.1 秒 |
| 上传的就是 PDF | 0（不用转） | 0.13~0.5 秒（75 页 0.5 秒） | 同左 |

也就是：Word 的「解析」基本就是 LibreOffice 转 PDF 的耗时——结果页要「跟直接打开原文件一个样」，
只有 PDF 做得到（见上面「坐标与结果页高亮」）。转换耗时随内容量走，26 页带表格的合同一次约 0.55 秒
已经是它的正常水平；读取文字本身只占 0.02~0.2 秒。

另外两处「谁先来谁吃亏」的冷启动，现在都在服务启动时预热掉了：

- **解析的进程池**（`warm_parse_pool`）：池是第一次真解析才建的，要现开子进程、每个子进程再 import
  一遍 pymupdf，实测约 0.57 秒。这笔开销以前整个算在「服务起来之后第一份文档」的解析耗时里，
  现在启动时就热上（放后台线程做，不拖慢启动）；正常退出时关掉（`shutdown_parse_pool`），
  不然每重启一次就留一批子进程在后台。
- **转换服务的 LibreOffice**（`warm_convert_server`）：它闲下来再被叫起来的那一次会慢一截
  （实测比连着用时多 0.2 秒上下）。启动时先用一个 900 字节的空 docx 点它一下，第一份 Word 就不用等这一下。
- 转换服务自身还有一个「每转换 N 次重启一次 LibreOffice」的机制（Gotenberg 默认 10 次），重启之后的那一次
  会从 ~0.17 秒跳到 0.55~1.1 秒（实测 30 次里 4 次，周期性出现）。手上这份起法把间隔调大了：

```bash
docker run -d --name gotenberg -p 3010:3000 gotenberg/gotenberg:8 \
  gotenberg --api-timeout=120s --libreoffice-restart-after=200
```

调大之后同样 30 次转换：中位 0.155 秒、没有周期性尖峰（只剩容器刚起时那次 1.0 秒的冷启）。

#### Word 解析（`correction/word.py`）

按 `w:p` / `w:tbl` / `w:sdt` 走一遍正文，取每个元素下所有 `w:t` 的文字：

- **内容控件（`w:sdt`）里的字照样读**。不能用 `paragraph.text`——它只认 `w:p` 的直接子 run。客户模板用控件填字段、贴条款，实测一份 6,927 字的合同里有 2,159 字藏在控件里（整条「第5条 价款支付…」、填入的「海男省三亚是」），模型以前从来没见过这些字。
- **表格按 `w:tr` / `w:tc` 取**，合并单元格不会像 `row.cells` 那样重复返回，格子里不会出现「一、需求单位: 一、需求单位:」这种假重复。
- **表格一个单元格一个纠错单元**（PDF、Word 同一个口径）：展平成单元格后各自送去纠错，太短、纯数字、纯标点的格子跳过。
- **表格走另一条路：先按编号定位到某一格，再在格内改**。每格行首挂一个**跨表唯一**的编号，形如 `2R3C7`（第 2 张表第 3 行第 7 列）；一个文档里多张表、有的行少几列、有合并单元格，编号都照样唯一。表格里本来就有大量一模一样的格子（合同价款 %、元（大写：）），指望"抄一段唯一引文"来定位是定不到的——实测同一张付款表里 4 处错字只能检出 1 处。行列号取解析结果里的真实位置，跟结果页展示用的是同一套数字。
  - 表格这条路的工具：`read_text` 顺着读，或者按 `table` / `row` / `col` 挑着读（`read_text(row=3)` 一次就把各表第 3 行端出来）；`get_cell(cell_id)` 按编号取某一格的完整内容；`find_cell(query)` 按内容找它在哪几格；`edit_cell(cell_id, old, new)` 在指定那一格里增删改（一样长=换字，少一字=删字，多一字=补字，连写=收成一个）。
  - **表格也分批送**：按单元格切批（绝不把一格切成两半，单格超限就自成一批），一批拼成一份 `000.txt`，跟正文一样分批并发跑阅读工具、再按编号合回各格——单表超过 `MAX_TEXT_LENGTH` 只是批数变多。
  - **合并单元格只在它的左上角出一格**（被它盖住的槽位是空的、本来就不送），所以编号会跳号（`1R2C1`、`1R2C4`，C2、C3 被横合并或空格吃掉了）——那只是没送纠错的槽位在跳号，合并关系仍由 `colspan` / `rowspan` 表达。
- **展示时表格照样是一张表**：每个单元格带上 `colspan`、`rowspan` 和它在表里的行列号（Word 读 `w:gridSpan` / `w:vMerge`；PDF 按单元格坐标还原被合并盖住的槽位），
  结果页靠这些把一格一格的结果按原样拼回表格——纠错拆开、显示合起来，两件事不互相将就。空单元格也留着，少一格整张表就错位了；
  十几列那种宽表不再往一屏里硬塞，给足最小列宽就地横向滚动。

两份测试文档都验证过：解析出来的字去掉空白后与 `document.xml` 正文的字符集合**完全一致**（无遗漏）。

#### 坐标与结果页高亮（`correction/pdf.py` + `correction/api.py`）

结果页要「跟直接打开原文件一个样」，所以除了文字，解析还顺手把**每个字在页面上的方框**取出来
（`page.get_text("rawdict")` 的字符流；表格单元格用「字中心落在格子里」筛出来，再按「去掉空白后逐字相同」
跟 `table.extract()` 的文字对齐）：

- 字符流跟 `get_text("words")` 的分词口径一致（都跳过半角空格），两边同序走一遍就能把「第几个字」对上
  「页面上哪一块」；对不上（字体缺字、编码怪、页面被旋转）**那一页干脆不出方框**——宁可没有高亮，也不能把框标到别的字上。
- 页面上每处改动按 `[x0, top, x1, bottom]`（PDF 坐标，左上角原点、单位磅）回给前端，同一行的相邻字合成一个框；
  多字改动（「直到」→「指导」）、连着删几个字都是一整个框。框的坐标跟浏览器里 PDF 画布用的是同一套，所以一定落在原字上。
- 表格**一格一个纠错单元**，改动就框在那一格里的那几个字上；格内文字跟坐标对不上时退回「整格标注」（比如文字分了两层叠着画的 PDF）。

### 接口

- `GET  /health` — 轻量存活检查（不连模型、不花 token，容器健康检查用它）
- `GET  /health/correction` — 纠错链路深度自检（真跑一次纠错，需要时手动调）
- `GET  /config` — 前端能力开关：配没配外部解析服务（配了就把页面上「文本纠错」「文档纠错」两条手工入口收起来，只留「纠错记录」和「链接纠错」）
- `POST /correction` — 上传 PDF / 办公文件（`file` 字段 Multipart），返回段落与表格中的纠错差异。带 `?full=true` 时额外多回这几样（不带时响应与之前**完全一致**）：
  - `blocks`：按正文顺序的全文分段（每段自带 `errors`）；表格单元格还带 `table` / `row` / `col` / `colspan` / `rowspan`，结果页据此把表格拼回原样
  - `highlights`：每处改动标在页面的哪儿——`{ index, page, tag, rects, original, corrected }`，`rects` 是 PDF 坐标（左上角原点、单位磅），相邻的同类改动已经合并成一处的口径跟清单一致
  - `doc_id` / `pdf_url` / `source_kind`：结果页要展示的那份 PDF（`source_kind` 是 `pdf` / `office` / `office_text`）
- `timings`：`parse_ms` / `convert_ms` / `correct_ms` / `total_ms`，解析和纠错各花了多久，前端的「纠错记录」就是拿它显示的（上传 Word 时 `parse_ms` 含 Word→PDF 转换，`convert_ms` 是其中转换那一段；`fileUrl` 那条路里取原件跟解析并行跑，`parse_ms` 就是解析本身）
- `GET  /document/<doc_id>` — 取回结果页要展示的 PDF（原始 PDF，或 Office 转换出来的那份），`Content-Disposition: inline`、可缓存、支持 `Range`（PDF.js 靠它渐进加载）。配了对象存储就从对象存储取：配了对外地址（`S3_PUBLIC_ENDPOINT`）直接 307 到带签名的临时地址（浏览器直连，后端一个字节都不搬），没配就由后端转发。没配对象存储则退回本机磁盘那份——那是唯一的原文，只留 `DOC_TTL_HOURS`（**被纠错记录引用的那份例外**：记录在库里长期保留，原文就跟着留，记录删掉之后才按 TTL 清）；配了的话本机不留长期那份，只有对象里取不到才走这个兜底
- 其它查询参数：`limit=N` 只处理前 N 段（调试用），`debug=true` 附带阅读工具调试数据
- `POST /correction_text` — 对单段文本纠错（`{"content": "..."}`）
- `POST /openapi/contract-audit/web-correct` — 对外接口（合同审查那边的网页调这个），**行为保持不变**：文本走 `content`、文件走 `file`、文件链接走 `fileUrl`（**都是表单字段 / form-data**，发 JSON 请求体或者把 `content` 放查询串里都不作数，会回 `400 content（文本）、file（文件）和 fileUrl（文件链接）至少要给一个`），三个都给时以 `file` 为先、其次是 `fileUrl`。`fileUrl` **一律由我们下载**回来、再走和 `file` 一样的链路（Word 等先转 PDF）。**这条接口跟有没有配外部解析服务无关**：一律走本地解析，配了也不会交给外部解析服务。结果都会存成一条纠错记录，响应里多回 `url`（能直接打开的结果页链接）和 `record_id`（记录库连不上时回 `null`，纠错本身照常返回）。`type` 标明走的是哪条：`file` 时 `results` 是逐段、逐格的纠错差异（带 `?full=true` 就多回全文分段和高亮框），`text` 时是逐字结果（`original_text` / `correct_text` / `errors`）。
- `POST /openapi/contract-audit/web-correct-DocParser` — 新接口，**只收 `fileUrl`**（文本、上传文件走原接口）：配了解析服务时链接原样转交（我们不下载、不转格式，那边报什么错就原样回给调用方，HTTP 状态码按它 `errorCode` 的段位来）；没配就退回跟原接口一样由我们下载、本地解析。本站页面「链接纠错」用的就是这个，其他调用方想走解析服务直连也用它。
  链接挂在哪个地址上优先看 `PUBLIC_BASE_URL`，没配就按这次请求的地址推（外部调的是前端端口，nginx 把 Host 透传过来，推出来的就是用户能打开的那个地址）
- `POST /review_contract` — 上传 DOCX/DOC 合同模板（`file` 字段 Multipart），提取所有占位符字段并逐字段审查

纠错记录（存 MySQL，见 `MYSQL_DSN`）：

- `GET  /records` — 记录列表（按时间倒序，只回列表页要显示的几列），`?limit=&offset=` 分页
- `POST /records` — 存一条记录（字段就是结果页要用的整份数据：`units` / `blocks` / `highlights` / `doc` / `timings`…），回 `{ id, createdAt }`
- `GET  /records/<id>` — 取一条记录的整份内容，结果页就靠它
- `PUT  /records/<id>/ignored` — 标记哪些是误报不用改（`{"ignored": [1, 3]}`，空数组是全部恢复）
- `DELETE /records/<id>` — 删一条记录，连带把没人再引用的原文 PDF 也清掉

没配 `MYSQL_DSN` 时这几个接口一律回 **503**（`detail` 说明「记录只存在浏览器本地」），
前端据此自动退回浏览器本地存储——纠错本身一点不受影响，只是结果链接换台机器打不开。

### 前端（独立镜像）

纠错前端在 `frontend/`（Vue 3 + Vite），**单独一个镜像**，跟后端镜像完全分离：只通过 HTTP 调本仓库的接口。
纠错结果页由前端自己渲染（`#/result/<id>` 这个 hash 路由）；结果与「纠错记录」由后端存进 MySQL。

结果页直接用 **PDF.js** 把原文件一页页画出来（`frontend/src/pdfdoc.js`），改动再按后端给的坐标贴成高亮框——
跟直接打开原文件看到的一模一样，不存在「排版被重排过」的问题。Word/Excel/PPT 也走这条路：
上传时后端先转成 PDF（`CONVERT_SERVER`），转成之后跟 PDF 完全同一条链路。

- 只画视口附近的页（滚动位置自己算），几十页的合同不会一次铺出几十张画布；滚远的页把画布放掉，内存不会一路涨。
- 改=琥珀、删=红（无删除线）、增=绿；当前这一处保留类型底色，外面再圈一道蓝。
- 后端没托管 PDF 时（没配 `CONVERT_SERVER`、或老记录）自动退回「把文字重排出来、在字上标色」那种渲染，功能不丢。
- PDF.js 的 worker 是 `.mjs`，nginx 老版本自带的 `mime.types` 不认它——`frontend/nginx.conf` 里补了一条
  `location ~* \.mjs$ { default_type application/javascript; }`；如果由外面的网关托管静态文件，也要保证 `.mjs` 回 `application/javascript`，
  否则结果页只会显示「Setting up fake worker failed」。

```bash
docker build -t text-correction-web:latest ./frontend
docker run -d -p 8080:80 -e CORRECTION_UPSTREAM=http://text-correction:32546 text-correction-web:latest
```

- 页面上的 `/api/*` 由容器里的 nginx 反代到 `CORRECTION_UPSTREAM`（默认 `http://text-correction:32546`），浏览器看到的是同源请求，不受跨域限制；外部系统调 `/openapi/*` 也由它原样透传过去（不剥前缀），所以整套服务对外只需要前端这一个端口。
- 用的是 `POST /correction`（PDF/Word，带 `?full=true`）、`POST /correction_text`、`GET /health/correction`、`GET /config`、
  以及记录那一组 `GET/POST /records`、`GET/DELETE /records/<id>`、`PUT /records/<id>/ignored`。
- `/correction` 的 `results` 仍然只回**检出错字的段落**（老调用方不受影响）；结果页要的全文由 `blocks` 提供，
  解析口径跟纠错单元完全一致，所以改动位置不用前端再猜。
- 「文本纠错」和「文档纠错」共用同一个结果页，只是入口不同（粘贴文本 / 上传文件）。
- 进页面先问一句 `GET /config`：配了外部解析服务时，那两条手工入口就收起来，只留「纠错记录」和「链接纠错」
  （粘一个文件链接就走对外接口那条路，后端下载后跑完，直接跳结果页）——那种部署下纠错主要是外部系统走 API
  调进来的，页面再摆手工入口只会让人绕着走。没配、或者 `/config` 拿不到（后端老版本、网络不通）就照旧三个页签。
- 结果页的标记只标具体改到的字：改字=琥珀、删字=红（无删除线）、增字=绿；不上底色、不划线。右侧清单只显示「类型 + 原文 → 改后」，页头只留文件名和上/下一处的导航。
- 右上角 `‹ ›` 或键盘 `←` `→`（`↑` `↓` 同义）直接跳到上/下一处，循环、自动居中。
- 结果和「纠错记录」存在**后端 MySQL** 里（`MYSQL_DSN`），所以同一个 `#/result/<id>` 链接换台机器、
  换个浏览器都能打开，原文也按打开链接的那台服务去取。后端没配库时记录接口回 503，前端自动退回
  浏览器本地存储（`localStorage`）：功能不丢，只是链接不通用；库里能连上之后，浏览器里攒下的旧记录
  会在下次进页面时一次性导进去（按 id 覆盖，链接照旧能用）。
- CI 里前端镜像是独立的 tag（`:standalone-web-x86` / `:standalone-web-arm64`），跟后端镜像分别构建、分别推送；我们自己的 tag 前缀是 `standalone-`，客户那边的 `legacy-*` / `legacy-*` 一个都不覆盖，推的是同一个仓库。
- 细节见 `frontend/README.md`。

### 一套起全（docker compose）

`docker-compose.yml` 把五件事一次起齐：原文对象存储（MinIO）、记录库（MySQL）、文档转换（Gotenberg）、后端、前端。

```bash
cp .env.example .env    # 填上模型凭据（OPEN_AI_*）
docker compose up -d
# 浏览器打开 http://localhost:18080
```

- 端口：**只有前端 `18080` 对外**——用户页面、结果页、对外接口都走它。后端、MinIO、MySQL、Gotenberg 都在 compose 网络里按服务名互访，不发布端口，服务器上不留多余入口。本机想直连后端或看 MinIO 控制台，`docker-compose.override.yml` 会把 `32546` / `9000` / `9001` 绑在 `127.0.0.1`（局域网进不来）。
- 构建出来的就是单跑时那两个镜像（`text-correction:latest`、`text-correction-web:latest`），跟手工 `docker build` 的 tag 一致，不会另起一个名字；五个容器都带 `restart: unless-stopped`，机器重启后自己回来。
- 数据都在命名卷里（`mysql-data` / `minio-data`），`docker compose down` 不删，`down -v` 才清空。
- 桶和表都是启动时自动建的，不用手工初始化。`MYSQL_ROOT_PASSWORD` / `MYSQL_PASSWORD` / `S3_ACCESS_KEY` / `S3_SECRET_KEY` 不填就用文件里的默认值，正式环境记得改。
- 想让浏览器直连对象存储（后端不搬字节）：在 `.env` 里设 `S3_PUBLIC_ENDPOINT`，填**浏览器能访问到**的地址，本机是 `http://127.0.0.1:9000`（靠 `docker-compose.override.yml` 那条本地端口），服务器上要么留空、要么填网关把对象存储暴露出去的那个地址；留空就由后端转发，任何网络环境都能跑。后端自己不去连这个地址，只拿它算签名，所以填一个后端连不上的地址也没问题。

### 服务器部署（只放两个文件）

服务器能出网（能拉镜像仓库和 Docker Hub）时，整套部署就是「一个 yml + 一个 env」：

1. 把仓库根的 `docker-compose.yml` 拷到服务器的部署目录。
2. 同目录放一个 `.env`：从 `.env.example` 拷一份，填好模型凭据，并把两个镜像地址指到仓库里（CI 推上去的那两个 tag，按服务器架构选 `-x86` / `-arm64`）：

   ```bash
   CORRECTION_IMAGE=ghcr.io/yuanshuai/text-correction:standalone-x86
   CORRECTION_WEB_IMAGE=ghcr.io/yuanshuai/text-correction:standalone-web-x86
   ```

3. 起服务（私有仓库先 `docker login`）：

   ```bash
   docker compose pull && docker compose up -d
   ```

   `docker compose ps` 看到五个都 `healthy` 就成了，浏览器开 `http://<服务器IP>:18080`。升级就是改 `.env` 里的 tag（或 `latest`）再 `docker compose pull && docker compose up -d`，数据卷不动，随时能切回上一个 tag 回滚。

   compose 里那两行 `build:` 在服务器上是用不到的（镜像都在，就不会去构建），想干净可以直接删掉。

   服务器上只有一个对外端口：`.env` 里的 `FRONTEND_PORT`（撞端口改这一行就行，不用动 yml）。另外三个（`BACKEND_PORT` / `MINIO_PORT` / `MINIO_CONSOLE_PORT`）只有本机那份 `docker-compose.override.yml` 用得上。

   nginx 反代「等后端回话」的时长是 `.env` 里的 `PROXY_TIMEOUT`（默认 `7200s` = 2 小时）：**它必须比「等解析结果」（`PARSE2JSON_MAX_WAIT_MIN`）+ 纠错那段时间更宽裕**，不然大文档会被 nginx 掐成 504。动了上面那个等待时间，记得一起看这个值。

### 离线一键包（服务器不出网）

服务器连不上 Docker Hub / 镜像仓库时，在能出网的机器上打一个包，整包传过去：

```bash
python deploy/pack.py              # 全套：mysql / minio / gotenberg 也一起打进去，服务器完全不用联网
python deploy/pack.py --minimal    # 只打自己的两个镜像，官方镜像让服务器自己拉
```

产出 `deploy/dist/text-correction-<日期>.tar.gz`（全套约 1.3G）。服务器上：

```bash
tar xzf text-correction-*.tar.gz && cd text-correction-*/
./install.sh
```

`install.sh` 会依次检查 Docker、检查 `.env` 必填项（缺哪几项会指名道姓地说）、装载镜像、起容器、等健康检查通过，最后打印访问地址和自检命令。细节见 `deploy/README.md`。

### 启动配置（环境变量）

服务通过 `.env` 或 `-e` 加载配置。必需变量缺失会直接报错，不会静默使用默认值。

#### 公共运行参数（两种模式通用）

| 变量 | 默认 | 是否生效 | 说明 |
| --- | --- | --- | --- |
| `LOG_LEVEL` | `INFO` | 生效 | 日志级别：`DEBUG` / `INFO` / `WARNING` / `ERROR` |
| `MAX_TEXT_LENGTH` | `3000` | 生效 | 一份 `000.txt`（交给模型读的那个文件）最多多少字；更长的文本在句末切分后分片并发纠错，不拒绝请求 |
| `MAX_CONCURRENCY` | `10` | 生效 | 并发处理 LLM 任务的最大数量 |
| `PDF_PARSE_WORKERS` | 按核数取，最多 8 | 生效 | PDF 解析开几个进程：按页并行，1 表示不并行（容器里 gunicorn 每个 worker 各有一份进程池，别开太大） |
| `LLM_TIMEOUT` | `60` | 生效 | 单次 LLM 请求超时秒数 |
| `LLM_TLS_VERIFY` | `false` | 生效 | 是否校验 LLM 网关 HTTPS 证书；默认关闭，需要校验时设为 `true` |
| `CONVERT_SERVER` | 空 | 生效 | Word/Excel/PPT 转 PDF 的服务地址（Gotenberg 那套：`POST {CONVERT_SERVER}/forms/libreoffice/convert`）；不配就跳过转换，Word 退回「文字重排」渲染 |
| `CONVERT_TIMEOUT` | `120` | 生效 | 调转换服务的超时秒数 |
| `PARSE2JSON_BASE_URL` | 空 | 生效 | 外部解析服务地址（DocParser：`POST {地址}/async/parse2json`）：配了就只走它，出岔子直接报错、不退回本地解析 |
| `PARSE2JSON_TOKEN` | 空 | 生效 | 调解析服务的 `X-Token` |
| `PARSE2JSON_ENABLED` | 配了地址就是 `1` | 生效 | 显式开关：写 `0` 就只跑本地解析 |
| `PARSE2JSON_FILE_URL` | 空 | 生效 | 给解析服务下载原文的地址模板，必须带 `{doc_id}`；只对上传的 `file` 用得上（`fileUrl` 是原链接转交）；配了 `S3_PUBLIC_ENDPOINT` 时优先用对象存储签名地址，可以不填 |
| `PARSE2JSON_TIMEOUT` / `PARSE2JSON_MAX_WAIT_MIN` | `60` / `60` | 生效 | 单次请求超时（秒）、从提交到拿到结果最多等多少**分钟**（超了这次纠错就报错）；老名字 `PARSE2JSON_MAX_WAIT`（单位秒）也认，会折成分钟 |
| `PARSE2JSON_POLL_INTERVAL` | `1` | 生效 | 隔几秒查一次解析结果 |
| `PARSE2JSON_MAX_PAGES` | `0` | 生效 | 最多解析多少页，`0` = 用服务端默认（1000，超了服务端回 `41301`） |
| `PARSE2JSON_OCR` | `false` | 生效 | 是否让解析服务对图片块做 OCR（扫描件、图片型表格） |
| `DOC_CACHE_DIR` | 系统临时目录下的 `correction-docs` | 生效 | 结果页要展示的 PDF 放哪儿；**只有不配对象存储时才用得上**——配了的话本机只放一份解析用的临时文件（在系统临时目录里，一趟请求结束就删） |
| `DOC_TTL_HOURS` | `24` | 生效 | 上面那个目录里的原文保留多久（**不配对象存储时**那份原文是要长期留的，被记录引用的还跟着记录走）；过期在下次写入时顺手清掉 |
| `S3_ENDPOINT` | 空 | 生效 | 原文 PDF 放哪个对象存储（MinIO / 任意 S3 兼容）：`http://主机:端口`。不配就把原文写在容器本机磁盘——单副本能用，一扩副本或容器重建就会丢文件（记录还在、链接点开没原文） |
| `S3_PORT` / `S3_USE_SSL` | 空 | 生效 | 端口、是否加密；都空着就按 `S3_ENDPOINT` 里写的端口和协议判断 |
| `S3_ACCESS_KEY` / `S3_SECRET_KEY` / `S3_BUCKET` | 空 | 生效 | 凭据和桶名：跟地址一样都不空才启用；桶不存在会在启动时自动建 |
| `S3_PREFIX` | `correction/` | 生效 | 对象名前缀（对象名是 `前缀 + 文档id.pdf`）；跟别的服务共用一个桶时用它错开目录 |
| `S3_PUBLIC_ENDPOINT` | 空 | 生效 | 浏览器也能访问到的对象存储地址：配了就让浏览器直连（`/document/<id>` 回 307 + 签名地址），不配由后端转发 |
| `S3_PRESIGN_SECONDS` | `3600` | 生效 | 直连模式下签名地址的有效期（秒） |
| `S3_TIMEOUT` | `30` | 生效 | 对象存储读写超时秒数（连接超时固定 5 秒；连不上会记日志并退回本机那份） |
| `MYSQL_DSN` | 空 | 生效 | 纠错记录存哪个库：`mysql://用户:密码@主机:3306/库名?charset=utf8mb4`；不配就是「记录只存在浏览器本地」，记录接口回 503、前端自动退回本地存储 |
| `MYSQL_HOST` / `MYSQL_PORT` / `MYSQL_USER` / `MYSQL_PASSWORD` / `MYSQL_DATABASE` | 空 / `3306` | 生效 | 不想写整条 DSN 时分开传（`MYSQL_DSN` 优先） |
| `MYSQL_RECORD_TABLE` | `correction_record` | 生效 | 记录表名；跟别的服务共用一个库时改一下就能错开，建表是幂等的 |
| `MYSQL_POOL_SIZE` | `2` | 生效 | 每个 worker 在连接池里留几条连接（记录都是小读写，两条够用） |
| `MYSQL_CONNECT_TIMEOUT` / `MYSQL_TIMEOUT` | `5` / `10` | 生效 | 连库、单条读写各多少秒超时（超时就回 503，让前端退回本地存储，不把请求挂住） |
| `ENABLE_WORD_CORRECTION` | `false` | 生效 | `true` 时 `/correction` 支持 `.docx` / `.doc`（仅在转换服务不可用时才会走到，没有坐标，结果页退回文字重排） |
| `ENABLE_TEST_MODE` | `false` | 生效 | `true` 时 `/correction_text` 返回内置假纠错结果，不调用 LLM |
| `TOOL_MAX_TURNS` | `0` | 生效 | 一份 `000.txt` 最多来回几轮：读一段、改一处、再读下一段都算一轮；0 表示不设上限（正常出口是 `finish`+覆盖率 100%、或连着两轮既不读也不改），正数时作为防死循环的熔断 |

#### 模型接入

任何 OpenAI 兼容网关都是同一种接法：地址 + 模型名 + Bearer token。

| 变量 | 必填 | 说明 |
| --- | --- | --- |
| `OPEN_AI_MODEL` | 是 | 模型名，如 `qwen3.5-27b` |
| `OPEN_BASE_URL` | 是 | 网关地址，如 `https://llm.example.com/v1` |
| `OPEN_AI_TOKEN` | 是 | Bearer token，请求头 `Authorization: Bearer <token>` |

调用时会下发关闭思考的字段（`enable_thinking=false`）；网关有私有字段就通过 `LLM_EXTRA_BODY` 注入。

> 纠错引擎依赖 `tool_calls`：模型要自己调 `read_text` 把原文读进来。上线后第一件事打 `/health/correction`，`tool_calls=0` 就说明这条路由没在调工具，纠错会静默为空。

#### 本地启动

```bash
cp .env.example .env
# 编辑 .env，填 OPEN_AI_MODEL / OPEN_BASE_URL / OPEN_AI_TOKEN
python index.py
```

#### Docker 启动

```bash
docker run -d --name text-correction -p 32546:32546 -e OPEN_AI_MODEL=qwen3.5-27b -e OPEN_BASE_URL=https://llm.example.com/v1 -e OPEN_AI_TOKEN=<把真实 token 填这里> ghcr.io/yuanshuai/text-correction:standalone-x86
```

`OPEN_AI_TOKEN` / `PARSE2JSON_TOKEN` 会直接进 HTTP 请求头，启动时校验必须全是 ASCII。
填成文档里的占位符（如 `sk-你的token`）会在启动时直接报错，而不是发请求时才失败。

启动后验证：

```bash
curl http://localhost:32546/health              # 轻量，不花 token
curl http://localhost:32546/health/correction   # 深度自检，花 token：status=ok 且 tool_calls>0 才算真的通
```

> 注：`.env` 被 `.dockerignore` 排除，Docker 部署请用 `-e` 或 `--env-file` 显式传入。纠错结果不包含纯标点符号差异（标点改动会被自动忽略）。
