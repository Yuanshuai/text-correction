# 纠错服务对外接口文档

纠错服务对外提供两个接口：一个收文本 / 文件 / 文件链接，走本机解析；一个只收文件链接，交给外部解析服务（DocParser）。两者返回结构完全一样，都会把本次结果存成一条纠错记录，并回一个可以直接打开的结果页链接。

## 一、接口地址

| 环境 | 地址 |
|------|------|
| 生产 | `http://203.0.113.10:18083` |
| 测试 | `http://10.0.0.10:18081` |
| 本机 | `http://127.0.0.1:18080` |

> 接口没有登录鉴权，只对调用方开放；生产环境请在安全组里把来源限制到调用方的 IP。

## 二、接口一览

| 接口 | 收什么 | 解析方式 |
|------|--------|----------|
| `POST /openapi/contract-audit/web-correct` | `content` / `file` / `fileUrl` 三选一 | 一律本机解析（Office 先转 PDF） |
| `POST /openapi/contract-audit/web-correct-DocParser` | 只收 `fileUrl` | 配了 DocParser 就原样转交；没配则退回本机解析 |

两个接口的返回结构完全一样。

## 三、请求

### 3.1 请求格式

- 方法：`POST`
- 编码：`multipart/form-data`；只传文本或链接时也可以用 `application/x-www-form-urlencoded`
- 参数位置：**表单字段**。发 JSON 请求体、或者把参数拼在 URL 查询串里都不作数
- 可选查询串：`?full=true`（文件路额外返回全文分段和页面高亮框）
- 鉴权：无

### 3.2 入参

| 参数 | 类型 | 必填 | 适用接口 | 说明 |
|------|------|------|----------|------|
| `content` | string | 否 | 原接口 | 待纠错文本，最长 3000 字的段落会自动分批 |
| `file` | file | 否 | 原接口 | 待纠错文件，支持的类型见 3.4 |
| `fileUrl` | string | DocParser 必填 | 两个接口 | 待纠错文件的 http/https 链接；原接口由服务端下载后处理，DocParser 原样转交 |
| `full` | boolean | 否 | 两个接口 | 查询串参数。置 `true` 时文件路额外返回 `blocks` / `highlights` / `doc_id` / `timings`，默认 `false` |

**原接口的取值优先级**：给了多个时只用一个，`file` > `fileUrl` > `content`。

**原接口**：三个至少给一个，都没给回 `400`。`fileUrl` 由服务端下载（超时 120 秒、上限 50 MB），下载后跟直接上传完全同一条链路；Word / Excel / PPT 先转 PDF。这条接口一律走本机解析，跟有没有配 DocParser 无关。

**DocParser 接口**：只认 `fileUrl`，没给回 `400`（不会去看 `content` / `file`）。配了 DocParser 时链接**原样转交**：服务端不下载、不转格式、不换地址，它只吃 PDF 和图片；它报什么错就原样返回（`errorCode` 4 开头回 HTTP 400，其余回 500）。没配 DocParser 时，等同于原接口的链接路径：服务端下载后本机解析。

### 3.3 大小与超时

| 项 | 限制 |
|----|------|
| 上传文件 | 100 MB |
| 服务端下载链接 | 120 秒、50 MB |
| 等 DocParser 解析 | 最长 60 分钟（部署时可配） |
| 建议调用方超时 | 不小于 10 分钟，超长文档再放宽 |

### 3.4 支持的文件类型

| 类型 | 后缀 | 说明 |
|------|------|------|
| PDF | `.pdf` | 原生解析，带每个字的坐标，改动能框在原字上 |
| 图片 | `.jpg` `.jpeg` `.png` `.bmp` `.tif` `.tiff` | 先转 PDF；本机解析不 OCR，只有 DocParser 路径能读出扫描件的字 |
| Word | `.doc` `.docx` `.docm` `.rtf` `.odt` `.wps` | 先转 PDF 再走同一条链路 |
| Excel | `.xls` `.xlsx` `.xlsm` `.ods` `.et` | 同上，表格按单元格逐个纠 |
| PowerPoint | `.ppt` `.pptx` `.odp` `.dps` | 同上 |
| 纯文本 | `.txt` `.csv` | 也走转换，转成 PDF 后纠 |

判定只看文件后缀。扫描件 PDF、图片没有文字层，本机解析会回 `200` 但 `results` 为空；这类文件请用 DocParser 接口。

### 3.5 请求示例

走文本：

```
curl -X POST 'http://203.0.113.10:18083/openapi/contract-audit/web-correct' -F 'content=这是一个纠错温本'
```

走文件：

```
curl -X POST 'http://203.0.113.10:18083/openapi/contract-audit/web-correct' -F 'file=@合同.pdf'
```

走文件链接（DocParser）：

```
curl -X POST 'http://203.0.113.10:18083/openapi/contract-audit/web-correct-DocParser?full=true' -F 'fileUrl=https://link.apadog.com/toUrl/2026/10/19/4625.pdf'
```

用 Apifox 时把 Body 切成 `form-data`：`content` 类型选 text，`file` 类型选 File，`fileUrl` 类型选 text；Headers 不用手工填 `Content-Type`。

### 4.3 顶层字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `type` | string | `text`（文本）/ `file`（文件，含文件链接） |
| `correction_count` | int | 本次纠了多少**处**，见 4.9 |
| `record_id` | string 或 null | 纠错记录 id，就是 `url` 里那段；记录库连不上时为 `null` |
| `url` | string 或 null | 能直接打开的结果页链接；记录库连不上时为 `null` |
| `results` | object 或 array | `text` 时是单个对象；`file` 时是数组，逐段 / 逐格，只含有改动的段 |
| `data.results` | 同 `results` | 双写副本，兼容老客户端，内容完全一样 |
| `code` | int | `0` 表示成功 |
| `messages` | string | 提示信息，正常是「任务完成」 |
| `engine_status` | string | `ok` / `degraded`（模型网关抖动但结果照常返回） |
| `blocks` | array | 仅 `full=true`：按正文顺序的全文分段，段落与表格单元格交错 |
| `highlights` | array | 仅 `full=true`：改动贴在页面的哪儿，长度就是「处」数 |
| `doc_id` | string | 仅 `full=true`：原文 PDF 的 id（32 位十六进制） |
| `pdf_url` | string | 仅 `full=true`：取原文的地址，就是 `/document/{doc_id}` |
| `source_kind` | string | 仅 `full=true`：`pdf`（原文就是 PDF）/ `office`（Office 转出来或图片转出来的） |
| `timings` | object | 仅 `full=true`：耗时明细，见 4.8 |

### 4.4 results 每一项

| 字段 | 类型 | 说明 |
|------|------|------|
| `original_text` | string | 这一段 / 这一格的原文，只去首尾空白，中间空格原样保留 |
| `correct_text` | string | 纠错后的文本 |
| `wrong_ids` | int[] | 有改动的字符下标，去重升序，等于 `errors` 里 `position` 去重排序的结果 |
| `errors` | object[] | 逐字改动明细，见 4.5 |

### 4.5 errors 每一项

| 字段 | 类型 | 说明 |
|------|------|------|
| `position` | int | 在 `original_text` 里的下标，从 0 开始；`insert` 表示插在这个下标的字符**之前** |
| `original_char` | string | 改前的字；`replace` / `delete` 时是原文里真实存在的字，`insert` 时是空字符串 |
| `correct_char` | string | 改成什么；`delete` 时是空字符串 |
| `tag` | string | `replace` 改 / `insert` 增 / `delete` 删 |

示例：原文 `这是一个纠错温本`，`position=6`、`original_char=温`、`correct_char=文`、`tag=replace`，表示第 7 个字「温」改成「文」。

### 4.6 blocks 每一项（仅 ?full=true）

| 字段 | 类型 | 说明 |
|------|------|------|
| `type` | string | `p` 普通段落 / `row` 表格单元格 |
| `text` | string | 该段 / 该格的原文 |
| `errors` | object[] | 该段 / 该格的改动，形状同 4.5 |
| `wrong_ids` | int[] | 该段 / 该格有改动的字符下标 |
| `table` | int | 仅表格格：第几张表，从 0 起，一个文档里跨表唯一 |
| `row` / `col` | int | 仅表格格：行号、列号，从 0 起 |
| `colspan` / `rowspan` | int | 仅表格格：合并了几列、几行，不合并是 1 |

表格是「一格一个纠错单元」：合并单元格会拆成多个 `row`，展示时靠 `table` / `row` / `col` / `colspan` / `rowspan` 拼回原表。

### 4.7 highlights 每一项（仅 ?full=true）

| 字段 | 类型 | 说明 |
|------|------|------|
| `index` | int | 处号，从 0 起，跟结果页清单的顺序一一对应 |
| `page` | int | 在第几页，从 0 起 |
| `tag` | string | `replace` / `insert` / `delete` |
| `rects` | array | 框在页面上的位置，每个框是 `[x0, y0, x1, y1]`，单位 1/72 英寸，原点左上；跨行时是多个框 |
| `original` | string | 改动前的内容；`insert` 时是空字符串 |
| `corrected` | string | 改动后的内容；`delete` 时是空字符串 |

### 4.8 timings（仅 ?full=true）

| 字段 | 类型 | 说明 |
|------|------|------|
| `convert_ms` | int | Office / 图片转 PDF 的耗时 |
| `parse_ms` | int | 解析（含等 DocParser）耗时 |
| `correct_ms` | int | 模型纠错耗时 |
| `total_ms` | int | 本次请求总耗时 |

### 4.9 「处」与「字」

`correction_count` 数的是「处」，`errors` 列的是「字」，两个数不一样是正常的。相邻的同类改动会合成一处：连着改几个字算一处、连着删几个字算一处、同一位置补几个字算一处。上面那份文件响应里 `errors` 有 6 条，其中 `position` 34（新改星）和 35（奇改期）相邻，合成一处。要「一共改了几处」用 `correction_count`；要「逐字定位、自己渲染」用 `wrong_ids` 加 `errors`。

### 4.10 结果页链接

`url` 指向的页面就是本站在结果页看到的那份东西：左边铺出原文件、改动框在原字上，右边是纠错报告，可以按文档顺序或按增删改类型看，也可以把误报忽略掉。链接可以转发，换台机器也打得开（记录存在服务端）。

链接地址优先取部署配置里的 `PUBLIC_BASE_URL`；没配就按这次请求的地址推，所以不管调用方从内网还是外网进来，拿到的都是同一个能打开的地址。

## 五、错误响应

| HTTP | 场景 | 响应体 |
|------|------|--------|
| 200 | 成功 | 正常业务响应；`results` 为空表示没有改动，或文档里没有可纠的文字 |
| 400 | 原接口三个参数都没给（含发 JSON、把参数放查询串） | `{"detail": "content（文本）、file（文件）和 fileUrl（文件链接）至少要给一个"}` |
| 400 | DocParser 接口没给 `fileUrl` | `{"detail": "fileUrl（文件链接）必须给一个"}` |
| 400 | 链接下载失败 / 超过 50 MB / 指向网页 / 空内容 | `{"detail": "..."}` |
| 400 | DocParser 判定链接有问题（不是 PDF、下不来等，`errorCode` 4 开头） | `{"detail": "外部解析服务解析失败：<它给的说明>（errorCode=40010）"}` |
| 400 | 文档转换服务不可用，且格式不是 `.docx` / `.doc` | `{"detail": "文档转换服务不可用：这种格式需要先转成 PDF 才能纠错..."}` |
| 500 | DocParser 连不上、超时、内部错误（`errorCode` 非 4 开头） | `{"detail": "外部解析服务解析失败：..."}` |
| 500 | 纠错任务内部异常 | `{"detail": "文档纠错任务失败"}` |

> `url` 和 `record_id` 在纠错记录库连不上时回 `null`，纠错结果本身照常返回，不因为存不上记录就失败。

## 六、对接建议

- 只纠一段文字用 `content`：最快，不经过解析。
- 手上有链接、文件有扫描件或复杂表格：用 DocParser 接口，链接原样转给它，效果最好。
- 链接必须是 PDF 或图片，DocParser 不认 Word / Excel；Office 文件请下载后用原接口的 `file` 上传。
- 同一份文件调两次会存两条纠错记录、两个结果页链接，互不影响。
- 只需要纠错结果、不需要页面：不传 `full`，响应更小、返回更快。
- 结果页渲染要的是 `full=true` 的 `blocks` / `highlights` / `doc_id`，自己渲染时按 4.6 / 4.7 的字段还原即可。
